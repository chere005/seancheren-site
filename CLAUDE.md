# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**CalMind** (`seancheren.com`) — a small multi-user app suite (Reminders · Calendar · Add · Notes · Habits, with Chat and Aki's Bookshelf alongside) in plain PHP on NearlyFreeSpeech.NET. CalMind is the suite's official name across web, iOS and Android — the login card wears it, and the native apps carry it as their display name; the individual apps keep their own names. No framework, no build step, no database, no dependencies. Each app is essentially one self-contained `index.php` that renders its own HTML/CSS/JS inline and posts back to itself.

## Commands

```sh
php -S 127.0.0.1:8787 -t public          # local server; apps at /calmind/reminders/, /calmind/calendar/, …
php tools/test.php                       # the test run — see TESTING.md
find public calmind lib tools -name '*.php' -exec php -l {} \;   # lint everything
./deploy.sh --dry-run                    # preview the (test) deploy, touch nothing
./deploy.sh                              # lint, then rsync to the TEST instance (/test/)
./deploy.sh both                         # …to TEST *and* production in one go
./deploy.sh promote                      # ship the live TEST tree onto prod, server-side
./deploy-dev.sh                          # lint, then ship a clean checkout to /dev/ ONLY
./deploy-dev.sh --dry-run                # preview the dev deploy, touch nothing
php tools/seed-example.php --force       # (re)build the "example" demo account
php tools/seed-buddy.php --force         # (re)build "buddy", example's sharing partner
```

`deploy.sh` is one-way (Mac → server) and deliberately never sends any `config.php`, never touches `/home/protected/data{,-test}/`, and never uses `--delete`. The Mac is the source of truth; if anything was hand-edited on the server, `rsync` it back down before deploying (see README).

**Three live instances share one source tree** (see "The /test/ sandbox mirror" and "The /dev/ slot" below), and **two separate scripts deploy them**. `./deploy.sh` owns **test and production** — `test` (default) → `/test/`; `prod` → the site root; `both` → both; `promote` → copy the *live test* tree onto prod server-side. A bare `./deploy.sh` is test-only, so production is never hit by accident. `./deploy-dev.sh` owns **`/dev/` and nothing else**: its destinations are constants with a guard that refuses any non-`/dev` path, so it cannot reach test or production, and `deploy.sh` names no `dev` path at all. That split is deliberate — someone working on `/dev/` and someone working on test/prod must not be able to collide. Both lint first, never send a `config.php`, never touch a data dir and never `--delete`. **`deploy-dev.sh` ships a clean `git` checkout, not the working tree** (`--ref <commit>`, default HEAD; `--dirty` opts back into the working tree): `deploy.sh`'s behaviour of shipping whatever is in `public/` right now is right for one person and wrong when someone else is mid-edit, since their half-finished work would ride along and a file written mid-rsync would ship torn.

Local login: users come from `lib/config.php` (gitignored; copy `lib/config.sample.php`). Local data lands in `./data/` and is unrelated to live data.

`tools/seed-example.php` builds a demo account — **example / examplepassword** — with plausible reminders (dated, undated, repeating, several overdue and still open), events across three calendars, notes and two months of habit history, all written relative to today so it never goes stale. It lands in `data/accounts.json`, like a sign-up, so `config.php` doesn't change. Neither `tools/` nor `data/` is deployed, so the live site needs it run *there* once — but **not over SSH**: `/home/protected/data/` is owned by the `web` user (`drwx------`), so a CLI run as the SSH login user hits *Permission denied* on every write (and the script prints "Seeded…" anyway, so the failure is silent). **Seed by running the script as the `web` user, i.e. over HTTP:** scp `tools/seed-example.php` plus a tiny throwaway wrapper (`<?php $argv=['x','--force']; require __DIR__.'/seed-example.php';`, guarded by a secret query param) into `/home/public/`, `curl` the wrapper once over HTTPS, then delete both files. Success shows as the *absence* of Permission-denied warnings; confirm by logging in as **example / examplepassword** on the live site.

## Layout and the web-root boundary

- `public/` → server `/home/public/`. Anything here is URL-reachable.
- `lib/` → server `/home/protected/lib/`. Shared code, never served.
- `data/` → server `/home/protected/data/`. JSON storage, never served, gitignored.
- `calmind/` → **CalMind's own top-level area in the repo, invisible to the server.**
  `calmind/public/` holds the five suite apps + `api/` (served at `/calmind/…` as ever)
  and `calmind/lib/` the lib files only CalMind uses (`tabbar`, `folders`, `sharing`,
  `palette`). Symlinks stitch it back into the served layout — `public/calmind` →
  `../calmind/public`, `lib/tabbar.php` → `../calmind/lib/tabbar.php`, … — so local
  serving, the preambles and the tests are unchanged, and both deploy scripts rsync
  with `-L` so the **server gets real files in the exact same layout as before the
  split**. Genuinely shared infrastructure (`auth`, `store`, `util`, `chrome`,
  `richtext`, `mail`, `usagelog`, `site`) stays in `lib/`, because chat, the bookshelf,
  akisthemes, userpalettes and the marketing pages use it too — a full duplicate lib
  was deliberately rejected: two copies of auth/store must keep session and encryption
  behaviour identical forever or logins/data quietly break. A new CalMind-only lib file
  goes in `calmind/lib/` with a symlink from `lib/`; a new shared one goes in `lib/`.
  The `deploy` test area guards the symlinks and the `-L`.

**The suite lives under `/calmind/`** — the five CalMind apps plus `api/` sit in `public/calmind/`, so production serves them at `seancheren.com/calmind/reminders/` and the mirrors at `/test/calmind/…`, `/dev/calmind/…`. Cross-app links build through `suite_path()` (`lib/auth.php`) = `suite_base() . '/calmind'`; the session cookie path and the apps outside the suite (chat, the bookshelf, the palettes pages) keep `suite_base()` alone, so one prod cookie still covers everything. The old roots (`public/reminders/` …) hold tiny 301 stubs that forward with the instance prefix and query intact, because installed home-screen icons and widget scripts still point there.

Every app page starts by locating `lib/` with the instance-aware preamble — copy it verbatim when adding a page. It picks `lib/` normally, but `lib-test/` when the page is served under `/test/` (it checks for `/test/` in `__DIR__` and in the request URI), so the sandbox mirror loads its own code. All data-touching pages carry the identical block, except that the suite pages under `public/calmind/` sit one directory deeper, so their relative `lib` candidates carry one more `../`; marketing pages (which hold no data) keep the plain `lib`-only preamble.

**The `/test/` sandbox mirror.** A second live instance of the whole suite runs at `seancheren.com/test/`, from the **same source** — there is no forked copy of the code. It is isolated in three ways: its pages load `lib-test/` (→ `/home/protected/lib-test/`), that lib's `config.php` sets `data_dir` to `/home/protected/data-test/` and `base` to `/test`, and `suite_base()` (`lib/auth.php`) prefixes every hardcoded cross-app link (`/calmind/reminders/`, the tab bar, `LOGIN_LANDING`, the widget link, icon/manifest hrefs) with that base. Redirects built from `_self_path()` already stay inside `/test/` for free — they bounce back to the URL that called them — so only genuinely cross-app links go through `suite_base()`. `lib-test/config.php` still **inherits production's**: it `require`s prod's `config.php` for the accounts and secrets and overrides only `data_dir` and `base`, so prod's logins are test's logins — a sandbox for *data*, not for *identity*. `/dev/` does not work this way (see below), and test could be moved to the same standalone shape whenever you want it; it is left alone here because changing it changes who can sign into a live instance. `deploy.sh` creates it once on the server (delete it to reset test). **Splitting it would lose nothing**: no config sets `data_key`, so every instance already generates its own `.datakey` inside its own data dir — the encryption was never shared. Test data lands in `data-test/`, auto-created by the web user on first write, so the sandbox starts as an empty suite. The `SUITE_BASE` env var forces the prefix without a config (mirrors `SUITE_DATA_DIR`), which is how the test run and a local `SUITE_BASE=/test php -S …` exercise it. **Change a cross-app link and it must go through `suite_base()`, or the mirror's link will jump to production** — the `test-instance` area guards this.

**The `/dev/` slot, a second fixed sandbox.** `seancheren.com/dev/` is a third live instance, built the same way as `/test/` — `lib-dev/`, `data-dev/`, `base` = `/dev` — added as one more hardcoded case beside the `/test/` check in every data-touching page's instance-aware preamble (not a generalized pattern-match; each new instance is its own literal branch, same as `/test/` is). `./deploy-dev.sh` pushes to it — its own script, which cannot write test or production; `promote` never reads from it — it stays out of the way of `/test/`'s own reviewed, ready-to-promote state. It exists so a feature in progress (first use: Aki's Bookshelf themes) can be poked at live, on a real device, without disturbing `/test/`. **The legacy p5 login that used to sit at `public/dev/` was renamed to `public/processing/` to free this path** — it had hardcoded `/dev/` in its own redirects, form action and script src, all re-pointed. A slug must not collide with any real app directory: the marker is matched against `__DIR__`, so an app whose own path contains the slug would load the sandbox's `lib-*` from production.

**The three instances have separate logins and separate sessions.** Two halves, and both are needed. *Accounts:* each sandbox config is standalone (above), so `app_users()` sees that instance's own `users` plus whatever signed up into its own `accounts.json`. *Sessions:* all three live on one domain, and a cookie set at path `/` is sent to every path beneath it — so the cookie **name** is the only thing that actually separates them. `session_cookie_name()` (`lib/auth.php`) derives one per *sandbox* from `base` (`SCSESS_TEST`, `SCSESS_DEV`; config `session_name` pins it) — **production deliberately keeps PHP's own `PHPSESSID` and its default session store**, because renaming its cookie would sign everyone out for nothing: it is the sandboxes that need to be different, not it. `session_store_dir()` gives each sandbox its own `sessions/` inside its own data dir, so even a session id copied from another instance finds no file. The sandbox cookie paths are narrowed to their base as well, which keeps a sandbox's cookie out of production's requests. Being signed into production must not sign you into `/test/` or `/dev/`; the `test-instance` area guards the naming, and the deploy area guards that no generated config inherits production's.

**The public top-level pages** (Home `/`, `projects/`, `about/`, `contact/`) are the site's marketing front, not part of the app suite: no login, no tab bar, no `chrome.php`. They share their own chrome through `lib/site.php` — `site_nav($active)` renders the pill nav and `site_page($active, $title, $bodyHtml)` wraps a page in the full HTML shell (dark theme echoing Reminders: `#111`/`#eee`/`#34d399`), with **the site's logo — a cursive SC (`.sitelogo`, Savoye LET, accent-coloured) — centred above the nav** and the matching baked icons linked (`/favicon-32.png`, `/apple-touch-icon.png`); the apps keep their own icons. Add a new static page by calling `site_page()` and adding its slug to the `$links` map in `site_nav()`.

## Core mechanics

**Storage.** All data goes through `store_read()` / `store_write()` (`lib/store.php`), which encrypt with AES-256-CBC under an `ENC1:` prefix. Reads transparently accept legacy plaintext JSON and re-encrypt on next write. Never `file_get_contents` a data file directly. Key comes from config `data_key` or an auto-generated `data/.datakey`.

**Per-user files.** `user_data_file($dir, $base, $user = null)` → `data/<base>-<user>.json`, defaulting to the signed-in user. Bases in use: `reminders`, `notes`, `events`, `calendars`, `calprefs`, `folders`, `habits`, `books`, `booknotes`, `shares`. `chat.json` and `token-<user>.json` are handled with hand-built paths.

**The clock.** `lib/auth.php` sets `date_default_timezone_set()` from config `timezone`, defaulting to `America/Chicago`. The server keeps UTC, so without it "today" turns over in the evening and the calendar advances a day early. Every page reaches this through `auth.php`.

**Auth.** `require_login('Area')` (`lib/auth.php`) — session-based, plaintext user⇒password map in config, `hash_equals` compare. One session covers the whole suite — *within one instance*; prod, `/test/` and `/dev/` each have their own (see "The `/dev/` slot"). **You stay signed in until you log out**: `session_boot()` sets a year-long cookie *and* a year-long `gc_maxlifetime`, and re-sends the cookie on every visit so the year always runs from now — both halves matter, since a long cookie pointing at a collected session file is still a logout. Anything that starts a session goes through `session_boot()`. A password the user changes themselves lands in the encrypted `data/passwords.json` and wins over the config entry, because `config.php` is hand-kept on the server and never deployed — delete that file to fall back to config. `require_login()` also seeds `$_SESSION['csrf']` and answers the settings window's `change_password` POST, so no app has to wire it up. **Signing in always lands on `LOGIN_LANDING` (`/calmind/calendar/`)**, whichever page asked for the login and whether it came through the password form or the sign-up code — one session covers the whole suite and the tab bar is a tap away, so "what's on today" shouldn't depend on which icon you happened to open. The login page itself is sized to `100svh` and never draws a scrollbar: it's one centred card over two fixed overlays, so there was nothing to scroll and the bar was the only thing moving on it. **Anyone can sign up from the login page**: `signup_handle()` takes a username, a valid email and a password, emails a four-digit code through `mail_send()` (`lib/mail.php` — an authenticated TLS SMTP session when config names `smtp_host`, plain `mail()` otherwise, with either failure logged to `data/mail.log`; `php tools/mailtest.php you@example.com` sends one test message), and parks the half-made account in `data/signups.json` for fifteen minutes (five wrong codes and it's gone). Only when the code comes back does it land in `data/accounts.json`, which `app_users()` merges with the config accounts — config wins on a clash. Nothing else in the suite is per-account gated beyond its own data files, so a new account is an empty suite; sharing is only between the pairs named in `SHARE_PAIRS`. Chat is deliberately public (no login). **Sending is currently switched off**: `signup_send_code()` has the `mail_send()` call commented out, logs a "would have emailed …" line instead, and every sign-up takes the fixed `SIGNUP_CODE` (`5678`) — so anyone who finds the login page can make an account. Turning real mail back on is un-commenting those two lines and restoring `random_int` in `signup_handle()`, once the SMTP credentials are in the server's `config.php`. `public/processing/` (renamed from `public/dev/` to free `/dev/` for the sandbox slot below) is a legacy standalone login unrelated to the rest.

**The usage log** (`lib/usagelog.php`, hooked in `lib/auth.php`). Every authenticated POST leaves one tab-separated line in `data/usage.log` — time, IP, username, app, the `action`'s name — and login/logout/sign-up log themselves (`login`, `login_fail`, `logout`, `signup_request`, `signup_badcode`, `signup_ok`). **Never any content**: the kind of operation only, every field squeezed to one clean token so nothing can smuggle a newline or someone's text into the file. Plain text (greppable, deliberately not encrypted — it holds nothing private beyond username and IP), per-instance for free since each instance has its own data dir, rotated once at 5MB to `usage.log.1`. The writer also self-heals the permissions the SSH login needs to `tail` it on the live host — group traversal on the data dir, group read on the log, nothing else — since the dir belongs to the web user (`drwx------`) and the SSH login only shares its group. **`tools/usagelog.sh` is the way to read it** (`-f` follows, `test`/`dev` pick an instance, `--real` drops the demo-account noise); it sources `deploy.conf` for the host like `deploy.sh` does, and bakes a literal tab into its filter so no quoting has to survive the remote shell. GET page views and the token-read endpoints (`feed.php`, `api/`) are deliberately not logged — a widget polls every few minutes and would drown the file.

**Mutations.** Every write is POST with a CSRF token from `$_SESSION['csrf']`, checked with `hash_equals`, then either a redirect (POST→redirect→GET) or, for AJAX callers, a `json_encode` response. AJAX posts send `X-Requested-With: XMLHttpRequest` and the handler echoes back the fresh authoritative state (e.g. the whole calendar list) rather than a bare `ok`.

**Sharing (opt-in partner lists, strictly mutual).** `lib/sharing.php`, which also owns the share window itself (`share_modal_html/styles/script`, `share_handle_set`). **Who shares with whom is a per-user list now, not a hardcoded pair**: each person keeps a `partners` list of usernames in their own `shares-<user>.json`, edited from the pencil at the bottom-left of the share window (a list of entries — add via the `+` row, rename via each row's pencil, remove via a two-press `×`; `partner_add`/`partner_rename`/`partner_del`, AJAX, answered by all three sharing apps). **A partnership exists only while BOTH lists name each other** — `share_mutual()` checks both stored files on every request inside `share_partner()`/`share_partners()`, the one gate every shared read goes through, so removal on either side ends all sharing instantly, both ways. The window badges each entry `sharing` (mutual) or `waiting for them`. `SHARE_PAIRS` (sean ⇄ aki, buddy ⇄ example) survives as *seed* entries: a user whose file has never carried the `partners` key acts as if it listed their pair partner, so the existing pairs work untouched and deleting the seeded name is the opt-out (`shares_save()` deliberately carries the `partners` bucket through untouched so a share toggle can't disturb it). The apps still show one partner at a time — `share_partner()` is the first mutual name on the list. The Share button and window render for **everyone** now (no partner required — the empty state explains the handshake and offers the pencil), and it opens from the **Settings window** in every sharing app (Reminders, Calendar, Notes) — the Share icon in the settings footer's three-button row — asking the page for the current lists through `window.shareData()`. It lists three kinds: calendars, reminder folders and note folders (`SHARE_KINDS` maps each kind to its bucket). Sharing is opt-in per item: nothing is visible to the other person until it's ticked. Nothing is ever copied: `shares-<user>.json` has three buckets — `calendars` (ids), `folders` (reminder folder names) and `notes` (note folder names) — and the reader loads the *owner's* file directly. Shared folders appear in the picker as `@<partner>:<Folder>`; when that view is active, reads *and* writes go to the partner's file, but structural edits (add/delete section, delete folder, reorder) are refused with 403. In the **All** listing a partner's block keeps its structure read-only, but its **ticks are live**: each row's check posts `view=@partner:Folder` (so it writes their file) with `ret=All`, which is the one value the redirect override accepts, so the tick lands back on All instead of jumping into the shared view. Reminders and Notes share the same shared-folder machinery — `shared_reminder_folders()` / `shared_note_folders()` validate a partner's shared list against what they still own on every read. Always re-check membership before touching a partner's data. **buddy ⇄ example is the demo pair**, built by `tools/seed-buddy.php`: the two are cooking dinner together over the next two weekends, so buddy shares out the reminder folder holding the grocery and dinner-prep checklists, the note folder holding the recipe, and the calendar carrying the two dinners — enough to show what sharing looks like without handing anyone a real account. That script is the only thing in the suite that writes another user's files, and it writes exactly two of them (example's events and example's `shares-`), from scratch each run so re-seeding can't double up.

**Recolouring a partner's shared folder.** Each person can recolour how the other's shared folders show *in their own picker*, using the lighter shared-palette variant (`app_palette($app, true)`). The override lives in the viewer's own `folders-<user>.json` under `colors.shared[$type]`, keyed by the full `@<partner>:<Folder>` view key, so it never touches the owner's data. `folder_shared_color()` resolves the colour: the viewer's override first, then the owner's own colour, then a shared-palette default by position. The recolour swatch is a read-only row under "Shared with me" in the folder manager; its `set_folder_color` post routes to `folder_shared_color_set()` when the name parses as a shared key.

**Lists with sections.** Reminders, notes, habits and book notes store section headers as rows in the same list (`['type' => 'section', …]`), guarded by an `is_section()`-style helper. Stored order is drag order; drag-reorder posts the new order via AJAX. A section header carries a blank drag-handle slot where it has nothing to drag (Reminders' two permanent groups, every Notes and book-note section), so its name starts level with the rows under it and with every other section's. Reminders additionally *displays* each group undated-first then by date, using stored order only to break ties — so dragging within a Reminders section is largely cosmetic, while dragging between sections and reordering sections still does what you'd expect. **That sort runs on outline blocks, not on rows**: `sort_by_date()` gathers each top-level reminder together with the `indent`-1 rows that follow it in stored order and sorts the blocks, so a subtask travels with its parent. Sorting the flat list tore a family apart the moment the two disagreed — an undated subtask under a dated parent sorted to the head of the section, where it read as a subtask of whatever now sat above it.

**Habits: week and month.** The bar above the grid picks one, remembered per user in `prefs-<user>.json` (`habits_view`, beside the theme). **Week** is the tick grid, paged by `?w=<n>` — whole weeks either way, from the ‹ › arrows or a firm sideways swipe on the grid, both going through the same links so they can't disagree. **Month** (`?m=YYYY-MM`) draws one cell per day, each a pie filled in proportion to how many of that day's habits were ticked — a `conic-gradient` of the accent over the empty colour, solid when everything got done, an outline for days still ahead. **Sections are managed from "Manage sections"**, the last row of the filter dropdown (`render_habit_section_modal()`): a window borrowing the folder manager's look (`.foldermodal` etc., already on the page via `folder_nav_styles()`) — an add row with a green `+`, a draggable list with a colour swatch and delete `×` per row, then Done. There's no inline "+ Section" any more. Add and delete are POST→redirect carrying `mgr=1`, which keeps them out of edit mode and reopens the window (a `sessionStorage` flag) rather than folding it away; recolour posts `set_section_color` and reorder posts the ordinary `reorder` action with an empty habit order (so only the sections move) in the background. **Sections are required.** `habits_normalize()` (run on read, persisted when it changed) guarantees at least one section — a fresh app opens with a default "Habits" section (stable id) — and re-homes any sectionless habit into the first section, so there is no ungrouped run. The last section is undeletable (deleting one moves its habits to the first remaining section); a default section is renameable like any other. Each section header carries its own **+ Habit** right of the name, shown whether or not you're in edit mode (`render_habit_add()` → `.hsec-add`), so a habit is added straight into that section; adding from outside edit mode doesn't drag you into it (`$stay` follows the posted `edit` flag). Reminders' and Notes' folder-head **+** (`.fsec-add`, adds a section) is likewise always shown now, not edit-mode-only. Holding a row/heading to enter edit mode no longer paints the text as a selection (ungated `user-select: none` on the hold targets, inputs opting back in). **Every section carries a colour dot** left of its name — the same swatch-opens-a-palette control the folder manager uses, shrunk to a folder heading's 11px, posting `set_section_color` in the background and recolouring in place. The colour is stored on the section row itself, keyed by id like everything else here, and comes from `app_palette('habits')` — Habits' own tier of the suite palette, the clockwise-leaned jewel shade (indigo, crimson, amber). Out of edit mode it is the same element with `pointer-events: none`, so turning editing on shifts nothing; in edit mode a transparent `::after` gives the 11px dot a 27px tap target. **Today** is marked twice in the week grid — a filled accent pill on the column head and a 2px accent ring on each cell under it — because the grid gap means a column tint draws as one faint patch behind the head and nothing below it. The month grid takes the same ring plus a filled chip on the day number.

**Habits rename in place.** A habit's name is editable by **double-click**, **long-press**, or a single tap while the Edit pencil is on — the label swaps for a field that posts `rename_habit` over AJAX (Enter or blur commits, Escape reverts), so the grid never reloads and nothing scrolls. Its sections still rename through `section_title_html()` like everywhere else.

**Renaming a section.** In edit mode a section's name is a field (`section_title_html()` / `section_rename_styles()` / `section_rename_script()` in `lib/chrome.php`): Enter or leaving it posts `rename_section`, Escape puts it back. Reminders, Notes and habits answer that action; `section_rename()` in `lib/util.php` moves the header and re-points every row that named it, refusing an empty or already-taken name. Habits key their sections by id, so they rename in place instead.

**Renaming a folder** (Notes). A Notes folder's name is editable in two places: **in edit mode** the list heading is a field (`folder_title_html()` / `folder_rename_styles()` / `folder_rename_script()` in `lib/chrome.php`, marker class `frename`), and **in the Manage-folders window** each of my own non-permanent rows is an editable field too. Both post `rename_folder`; `folders_rename()` (`lib/folders.php`) carries every reference across — the list, colour, hidden flag, drag order, catch-all index and the default/last-view prefs — and refuses a fixed (`General`), empty, unchanged or already-taken name; the app then re-points its notes and section rows from the old name to the new. Reminders folders aren't renameable this way (the picker/manager pass `allowRename` only for notes), since its `Reminders`/`Calendar` are permanent by name.

**Two dot legends.** The **Calendar** draws a key under the grid (both month and week views), in its own bar pinned *between* the calendar half and the day panel — not inside `.cal-top`, where it sat below the 60vh fold on a phone and never showed on open; the bar caps at `22vh`, scrolls within itself, and hides when the key is empty: one row per owner (mine, then a sharing partner), each grouped events → reminders → notes in the legend's kind order, listing every calendar/folder with an item in the drawn window under its own colour dot — a calendar glyph before the event dots, a checkbox before the reminders, a page before the notes (`cal_legend_icon()`; built straight off `$byDay`, so it matches the cells). **Habits' month view** draws its own key: each counted section with its colour dot, in the pie-slice order, so a day's pie reads back to its sections.

**Editing from the day panel is a two-step now**: a long-press or double-click only turns edit mode on, revealing each own row's icon cluster — pencil (opens the edit window), duplicate, delete ×, 26px circles like a Reminders row; a partner's rows get none. **The edit window's kind row comes back when editing an event or a reminder, cut down to [itself, Note]** (`constrainKinds`): picking Note makes the row the title of a new note (`edit_item` + `kindchoice=note` — the source is found and detached first, so a partner's id creates nothing; an event moves out entirely, a reminder with subtasks stays as their home). A note's own edits keep the row hidden — notes never convert out. **The Calendar add/edit modal hides Time and Repeat behind "+".** Both start hidden; a **+ Time** and a **+ Repeat** button reveal them, and each carries a `×` that folds it away again (JS: `revealTime`/`revealRep`). A note never repeats, so its whole repeat wrapper hides. In the repeat row the **count sits right before the unit selector** ("every `[N]` weeks"), the two on one line so they read as one control. The **Add** app grew a matching **+ Repeat** (reminders/events only) beside its **+ Date/Time**.

**Permanent folders.** Only reminders' `Calendar` (`FOLDER_CALENDAR`, `lib/util.php`) is permanent now — always present, undeletable, unrenameable, the sole entry in `folders_fixed('reminders')`, because its name *is* its identity (the ride-along below is keyed on it). `Reminders` (`FOLDER_REMINDERS`) and Notes' `General` (`FOLDER_DEFAULT`) are merely *seeded* for a new account (`folders_starter()`): both rename and delete like any other folder, except the last folder of a type is undeletable (`folders_delete()`), which in practice only bites in Notes. **Nothing may assume `General` exists** — a fallback resolves through `folder_default_get()` (or `folder_fallback()`, which for reminders is `Calendar`), never the literal name; the folder manager's delete hint once read `folders_fixed('notes')[0]` and was a live PHP warning. They used to be two permanent sections living inside every folder at once, which meant an item had a folder *and* a group and the group was sometimes really a folder. An *undated* reminder in the **Calendar folder** rides along on the calendar under today, every day, until it's ticked off — the Calendar page and `feed.php` both special-case it, and it must not be flagged `rolled`/overdue, since it isn't late. **There is no unnamed catch-all any more.** Every folder always holds at least one *real* section, and every reminder and note sits in one — `sections_normalize()` (`lib/util.php`) guarantees it on read, creating a default section named `SECTION_DEFAULT_NAME` (`General`) for any folder that has none and re-homing a blank-or-unknown-section item into its folder's first section. The default is a normal named section: **renameable** like any other, and **undeletable while it's a folder's only one** (deleting a non-last section moves its items into the folder's first remaining section, never to a nameless bucket). Both apps normalise their own file on load and write the repair back; a partner's shared list is normalised in memory only (their structure is theirs). Every writer that files an item — the app itself, the **Add** app, the Calendar day-panel, `quick.php` — resolves a blank/unknown section to the folder's first, so nothing lands loose. New items land in the **Default Folder/Section** chosen in the Manage-folders window (`set_default_section`, stored as `default`+`default_section`; the picker offers the same folder→section list the Add app does). `reminders_folder_migrate()` still brings an old list over — section `Calendar` becomes folder `Calendar`, folder `General` becomes folder `Reminders`, the old `Calendar` header rows are dropped. It's idempotent and cheap, so every reader runs it: Reminders writes the result back on its next save, while the Calendar, `feed.php` and `api/reminders.php` normalise in memory and never write.

**Empty sections in a folder view.** A section with no rows under the viewed folder is marked `.folder-empty` and hidden by CSS, not skipped server-side — it has to stay in the DOM so that a section you just created (which has no rows yet) is visible while editing instead of appearing to vanish. Anything that hides a group conditionally should hide it the same way, since the view is remembered across visits and `All` is usually *not* what you're on.

**Adding to Reminders.** Notes works the same way — its `+ Note` button is gone too. There is no New-item window in Reminders any more. Each section header carries a `+` immediately to the *right* of its name (in Notes it fires `add` directly; in Reminders it reveals an inline row) posting `action=add` with that `section`; the server runs the typed text through `parse_when_from_text()`. The delete `×` is pushed to the far right (`margin-left: auto`). New reminders, notes and sections are prepended, so they land at the *top* of their list/section. A collapse chevron (`section_collapse_button()`, `lib/chrome.php` — a small `>` that points down when open, right when collapsed) sits at the left of the name; tapping it folds the section (remembered per page in `localStorage`, hidden in edit mode where the drag handle takes that slot). **Subtasks:** one level, reminders only. In edit mode each row carries one control just left of its delete `×`, and which one depends on where the row already sits: a task gets a **+** (`subtask_button()`), which POSTs `add_subtask` and comes back with a blank subtask inserted directly under its parent — same folder, same section, `indent` 1 — and `?focus=<id>` telling the page to open it for typing; leaving it empty deletes it again. A subtask gets a **‹** instead, which lifts it back out through the AJAX `set_indent` and reloads (its sort position changes the moment it stops being part of its parent's block). The level is rendered as `padding-left` via a `--ind` CSS var, so the content shifts right while the delete `×` stays pinned to the right edge. The + used to indent the row you pressed it on, which is a different act entirely — it demoted an existing reminder instead of making a child of one. **The full-edit pencil** sits left of the duplicate button on every top-level own row (edit mode only, never on a partner's rows — a shared view also 403s the action): it opens `#convModal`, the Calendar's edit menu piece for piece (same "Goes in" label, same Delete/Cancel/Save row with the two-press Delete on the left), **with the kind switch live — Event / Reminder / Note** (`edit_full`). Saving as a reminder updates in place and can re-file it — its subtasks travel along. Saving as an **Event** writes the event into my events file (calendar re-validated, stray ids fall back to the default; an undated reminder converts onto today); saving as a **Note** writes a note titled with the text into the picked note folder/section (validated, falling back to the notes default; the repeat row folds away, notes don't repeat). **Conversion is one-way into notes**: a reminder or event can become the title of a new note, but a note never converts out. Either conversion removes the reminder — *unless it has subtasks*, which can't ride along, so then the reminder stays behind as their home and the window's hint says so. **The duplicate button** (`duplicate`, the two-squares glyph between the pencil and the subtask +) copies the whole outline block — parent and subtasks, fresh ids — directly under the original; Notes' rows carry the same button (`.ndup`, a plain note copy), and the calendar day panel's rows too (`duplicate_item`, block-copying reminders).

**The outline drag model.** The indent levels are read as an outline: **level 0** is a section, **level 1** is a subsection *or* a reminder sitting under a section, one more indent again is a sub-subsection or a sub-reminder. Dragging follows from that, and nothing moves until the drop — a single `.drop-line` (a zero-height accent border, an `<li>` inside a row list and a `<div>` between blocks) is the only feedback, because live-shuffling the real rows made it impossible to see what you were about to get. **Level 0 travels as a block**: `blockOf()` walks forward from the section over every following group with a deeper indent, so a section's subsections and rows always come with it, and it can only land between other level-0 blocks — never inside one. **Level 1 goes anywhere among level-1 things**: a reminder or a subsection can be dropped between any two rows in any list. Dropping a *subsection* among rows splits that list — everything from the line to the end of the list becomes its, which is exactly "up to the next subsection or section", since a list only ever holds one section's rows. **Drags cross folders now, in Reminders and Notes both**: a row dropped in another folder's list re-files there, and a whole section dropped in another folder's block moves with its rows — a partner's shared block is never a target (the drop line refuses it). The persisted shape is the same in both apps: `order` = `[{id, section, folder}, …]` off the DOM top-to-bottom, `sections` = a map `folder => [section id, …]` (the catch-all as `''`), and the handlers mirror each other — a section re-files **by id** (names collide across folders), a move into a folder whose *staying* sections already hold that name is refused (a duplicate loses items on delete; being listed in the map is not the same as leaving), and a stale flat-name payload from before this shape reorders nothing rather than guessing. The `drag` test area replays these payloads and checks everything sticks after a reload. **Dragging a folder's last section out asks first** — OK moves the section then deletes the emptied folder (two chained posts, so the writes can't race); Cancel reverts the drop; the permanent Calendar folder and the last Notes folder are never offered. `topOf()`/`isTop()`/`lvlOf()` read the level straight off the `--ind` custom property, so the DOM stays flat and there's no real tree to keep in sync. Creating an *event* or *note* happens in the Calendar and Notes apps, or from the **Add** app (`public/calmind/add/index.php`, the tab bar's middle **+**). Add takes a line of text, a type (Reminder / Event / Note) and — behind one pill whose label and panel follow the type — where it goes: folder and section for a reminder or a note, a calendar for an event. Each defaults to that app's own default (`folder_default_get()`, `calprefs.default_cal`) and is re-validated server-side on the way in.

**Repeats** (`lib/util.php`). A reminder or event may carry `repeat => ['n' => 2, 'unit' => 'day'|'week'|'month'|'year']` — "every 2 weeks"; absent or null happens once. There is only ever the one stored row: `repeat_dates($start, $rep, $from, $to)` expands it over whatever window the reader is drawing, so the Calendar expands across the month it renders and `feed.php` across its 21 days — both places need changing together, as ever. Month and year steps keep the day of the month and clamp it (the 31st repeats as the 30th, the 28th…) rather than sliding into the next month the way `strtotime('+1 month')` does. **Ticking a repeating reminder rolls its `due` to the next occurrence instead of marking it done** (`repeat_next()`, in both the Reminders app's `toggle` and the Calendar's `toggle_reminder`), so the row always sits on the next date it owes — and, like every dated reminder, an overdue one still shows on today. **A roll must be visible or the checkbox reads as dead**: both handlers append `rolled=<id>` to their redirect, and the page flashes that row (`.rolled-flash` — the Reminders list scrolls to it and lights its date chip; the day panel flashes it if it's still on the day, and a row that rolled off the day is its own feedback). Notes don't repeat.

**Text parsing** (`lib/util.php`). `parse_time_from_text()` pulls `2pm` / `2:30 pm`; `parse_date_from_text()` pulls `m/d`, `m/d/yy`, `m/d/yyyy` (bare `m/d` = next occurrence). `parse_when_from_text()` runs both and returns `[text, date, time]`. Date parsing is slash-only and US-order so it can't wander into other numbers, but it can't distinguish a date from a fraction — `2/3 cup` parses as Feb 3. An explicit date/time field from a form wins over the parsed one for the *value*, but a parsed token always leaves the stored title — it was an instruction, not part of the name, so "Dinner 8/3 with Sam" is titled "Dinner with Sam" whichever date wins (creating and editing, reminders and events alike). Adding *and* editing an item on the Calendar read the text the same way, so retyping "Vet 8/3 2pm" on an existing reminder moves it. Reminders carry an optional `time` alongside `due`.

**Note bodies are HTML** (`lib/richtext.php`). Notes and book notes are edited in a `contenteditable` (`.rt-body`) mirrored into a hidden `input.rt-value` named `body`, so autosave still posts an ordinary field. Everything is stored through `rt_sanitize()` — a DOMDocument allowlist (`b i u strong em blockquote ul ol li br div p span`, plus `class` only when it matches `rt-*`) — because the body is rendered rather than escaped. `rt_body_html()` spots a body with no tags at all as one of the old plain-text notes and escapes it, so nothing written before this needs migrating. `rt_toolbar_html(true)` adds the bookshelf-only `+✏️` window (next to the quote button) that inserts a quote, a note about it, a page number and an optional date stamp. The quote button toggles: pressing it inside a quote lifts *only the caret's line* out by hand — `formatBlock('div')` doesn't reliably strip a blockquote — and lines are found either as block children or as runs between `<br>`s, since Enter produces one or the other depending on the browser.

**Folder blocks in the All view.** When "All" spans more than one folder, Reminders and Notes wrap each folder's sections in a collapsible `.folder-block[data-folder]` headed by `.folder-head` — `folder_collapse_button()`, the folder's name, and a short right-aligned rule. **The folder's colour is the wash behind its name, not a dot beside it**: `folder_tint()` (`lib/folders.php`) renders it as 8-digit hex at 20% alpha on a `border-radius: 999px` chip, because at 11px a dot read as a full stop you had to go looking for, while a wash says the whole run under it belongs to that folder. Eight-digit hex rather than `color-mix()`, which is newer than some of the phones these run on; anything that isn't a plain `#rrggbb` gets no tint rather than a broken one. The picker and the section headers keep their dots. The name itself is near-white: the wash is what marks the heading as the level above the gold section titles, so the text only has to be legible, and near-white is the one value that reads on all six folder colours at once. `folder_collapse_script()` (`lib/chrome.php`) remembers the folded ones per folder in `localStorage`, keyed separately from sections so the two never collide. **Notes derives the folder list from its notes as well as its sections** (`$folderOrder`), so a folder shows a heading even before you add a section to it. The unnamed "Notes" catch-all (`render_note_default_group()`) now renders *only* when a folder still has loose notes — which normalisation removes, so in practice every folder shows its real sections (led by its default `General`) and nothing loose. **Every list heading is a collapse target**: a "collapse all" button (`collapse_all_button()`, `folder_collapse_all_script()` in `lib/chrome.php`) folds every `.folder-block` (or expands them all on a second press) — Reminders puts it left of Completed, Notes above the top folder; Habits wires its own to fold sections.

**Folders** (`lib/folders.php`) are a separate per-user filter; the permanent folders (`folders_fixed()` — reminders' `Calendar`; Notes has none) always exist and are undeletable. Both apps pick one from `render_folder_pick()` — a round colour button on the *right* of the top bar, by the username, dropping a menu grouped by owner, the same shape as the Calendar's calendar picker. **Manage folders** is the last row of that dropdown (`$manageLabel`, id `folderMgr`) rather than a button of its own; the Calendar's picker carries a matching "Manage calendars" row. Folders carry a colour from the per-app palette (`app_palette('reminders'|'notes')` in `lib/palette.php` — blue/red/green/orange/purple/grey, each app leaning the hues into its own unmistakable shade: reminders the vivid anchor, calendar electric-deep with a violet lean, notes leaned back and brightened (sky, rose), habits leaned on at full strength (indigo, crimson, amber); every own colour clears 3:1 on the dark card, and a partner's shared set is a matching lighter version of that app's own), stored under `colors` in the same file, defaulting by position so a new folder is distinct straight away; it's changed from the swatch on each row of the folder window, which posts `set_folder_color` — the swatch posts in the background (AJAX) and recolours in place, so the manager stays open. Adding, removing and choosing the default happens in `render_folder_modal()` — the window that dropdown row opens — which posts the ordinary `add_folder` / `delete_folder` / `set_default_folder` actions each page already handles, so it's plain POST→redirect, not AJAX. Deleting a folder keeps its items: both apps re-resolve the **Default for new items** *after* the delete (`folder_default_get()` skips the deleted name) and move them there, into its default section — never to a hardcoded fallback. **Every folder in the picker carries a show/hide checkbox, and the ticks are what's on screen.** Tapping the **box** toggles just that folder (`folder_vis`) **and lands on the All view** — the ticks describe the All canvas, and composing them from a single-folder view used to flip the stored flags while the screen kept showing just that folder, which read as the boxes doing nothing even across a refresh (the Calendar's box does the same, keeping its month and day). Tapping the **row** makes it the only one ticked (`folder_vis_only`) and then opens it, which is the quick way to look at one thing without unticking the rest by hand. **All** is the master: ticked only when everything is showing, so one tap shows the lot and a second — with them all already on — hides the lot (`folder_vis_all`). All three post in the background and reload to re-filter, then reopen the menu (`folderPickOpen` in `sessionStorage`). The picker sends the keys it drew along with the change, so `folders_set_visible()` can write my own folders (`hidden`) and the partner's shared ones (`hidden_shared`) in one go — the master used to touch only my own, which left one of theirs switched off by hand with no way back. The Calendar's picker is the same three gestures over `hidden_cals` (`cal_vis` / `cal_vis_only` / `cal_vis_all`). `folders-<user>.json` carries three prefs beside the lists, all keyed by type: `default` (where new items land while you're viewing "All"), `last` (the view to reopen on) and `hidden`. Like every stored id they're re-validated on read, so a deleted folder silently reverts.

**Calendars.** A calendar is `['id','name','color']` and an event carries a calendar id. **Renaming one** is the pencil on its row in Manage calendars (client-side field swap posting `cal_rename`, same AJAX group as add/recolour): only the name moves — everything references the id — and only my own rows carry the pencil, a partner's shared calendar isn't mine to rename. There used to be a second kind of row here — a "calendar set", a saved group of calendars viewed together — and it paid for itself nowhere: the picker, the manage window, the widget and the day panel each carried a branch for it. It's gone; `is_calset()` survives only so `load_calendars()` can drop leftover set rows on the next read. `calprefs-<user>.json` holds view prefs: `hidden_folders`, `hidden_shared_folders`, `default_cal` (which calendar new events land in when you aren't viewing one in particular) and `last_cal` (the selected calendar, persisted rather than session-scoped). The calendar page reads reminders, notes and events together (`kind_spec()` maps each kind to its file and its text/date field names). Adding a *reminder* from the day panel offers **every folder with its groups** (an `optgroup` per folder, values `folder\x1Fgroup`), never a calendar — a reminder belongs to a folder and a section, a calendar id would be meaningless on one, and since `Calendar` became a folder the picker has to reach it. **Whatever you just added has to be visible afterwards** or the add reads as having failed: `$showAgain()` widens `last_cal` back to `all` and un-hides the folder when the current filter would have swallowed the new item. The add window also resets both owner pickers (`ownerReset()`) each time it opens — they're sticky selects, and leaving the partner's set meant the next thing you added quietly went into *their* file. **Mine and the partner's stay in separate pickers**, never one merged list, so whose file a new item lands in is never a guess: the add window shows a calendar dropdown per owner (`cal` / `cal_shared`) and a group dropdown per owner (`section` / `section_shared`) — up to four rows, and six once notes join in. Only the partner's carries a blank `—`; picking from either side clears the other, so exactly one owner is ever selected. A shared choice writes to *their* file (`user_data_file(..., $partner)`), validated against `$sharedIds` / `$sharedFolders` on the way in. The partner's group values carry `folder\x1Fgroup` together, since a shared reminder needs both, and `\x1F` can't survive `folder_clean()`. Within a day, events come first in time order, then reminders, then notes. **A day's reminders are sorted undated-first, then by date, then by time** — the Reminders app's own order — which matters most on *today*, since today collects every overdue reminder as well as the undated Calendar-folder riders and the ones actually due; before that they arrived in whatever order the file happened to hold. **The day panel groups by kind *and* owner**: one collapsible `.dp-group` per pair, mine before the partner's, within the legend's kind order — "Events" then "Aki's events", and so on. `gkey()` (`kind` + `:owner`) is both the grouping key and the `localStorage` fold key (`calFold_<gkey>`), so folding "Aki's events" doesn't fold mine. The partner's headings are a shade dimmer; their rows carry no name chip any more, since the heading above already says whose they are. **A day is selected by a tap and nothing else.** Watching `click` meant every swipe across the grid selected whichever cell the finger lifted off, so a month you paged to opened on a day you never picked; selection is now pointerdown+pointerup on the same cell with under 10px of travel, and the swipe handler is free to ignore clicks entirely. **Week mode** is a swipe up on `.cal-top`: the server still renders the whole month, but each cell carries `data-week`, so the mode is only a class hiding the other rows (plus the legend and the calendar picker), and the arrows step one week at a time, crossing into the neighbouring month with `?wk=first|last`. It sticks in `localStorage` under `calWeekMode`. A firm *sideways* swipe on `.cal-top` pages by whatever the arrows do — a week in week mode, a month otherwise — so the gesture and the buttons can't disagree. A month cell draws the legend's kind icons instead of dots — **one per kind and colour** (`cal_legend_icon()`: calendar glyph, tick box, page), in the legend's order, colours in first-appearance order within each kind — so a day with events on two calendars wears two calendar glyphs, and the panel carries the per-item detail. The icons sit in a fixed two-row well (three per row on a phone), so every cell is the same height however busy the day; more than six and the cell keeps five plus a `+` in the sixth slot. Each reminder icon takes the worst state of *its colour's* reminders that day: overdue beats open, and it only greys out (hidden unless Completed) once every one of that colour is ticked. **The session's remembered day (`calDay`) restores only on a bare arrival** — `?ym=`/`?wk=` are deliberate paging, and restoring across them bounced every page-back straight back to the remembered day's month. The palettes viewer's calendar mock mirrors the same icons.

**The iOS widget** (`public/calmind/calendar/feed.php`) serves JSON to a Scriptable script, authenticated by a token in `token-<user>.json` rather than a session. The setup page bakes the calendars you're currently viewing into the generated URL as `&cals=<ids>` (or `cals=all`), so a widget keeps showing what you picked when you made the script — copy it again to re-point it. `feed_scope()` honours that pin (validated against your own calendar ids, so it can only ever narrow), and falls back to re-deriving the view from `calprefs` (`last_cal` + `hidden_folders`) when there's no pin or the ids are stale — which is also what older scripts without the parameter do. Reminder folders are never pinned; they always follow `hidden_folders`. It re-implements the file paths and filtering by hand — changes to how items are selected need making in both places. **The widget groups by day, not by kind**: one heading per date ("Today · Jul 31", "Sat · Aug 1") with a light rule directly under it and a heavier one between days, reminders before events within each day. **Notes never reach the widget**: `build_feed()` only emits reminders and events, dropped server-side rather than only in the generated script so a widget still running an older script stops showing them too. A reminder draws an **empty tick box** (`SFSymbol.named("square")`, tinted overdue-orange when rolled) where an event draws a dot, and carries its `id` so the row can link to `quick.php?tick=<id>`. Tapping the widget opens `public/calmind/calendar/quick.php`, a session-authenticated one-field page that appends a reminder or event for today (defaults `folder => folder_fallback('reminders')`, `section => ''`) — it also hand-builds its rows, so a new required field on reminders or events needs adding here too. `?tick=<id>` puts it in a second mode: that one reminder with a single **Done** button, whose POST (`action=tick`, CSRF-checked) marks it done or, for a repeat, rolls it to the next date via `repeat_next()`. The tick deliberately happens *there* rather than behind the feed's token, so the read-only-token rule above still holds.

**Token auth.** Anything that can't hold a session — the Scriptable widget, the watch app — authenticates with the string in `token-<user>.json` instead. `token_user($dir, $token)` (`lib/auth.php`) does the lookup for all of them; `feed.php` still owns *making* the token, on the widget setup page. The token is a **read** credential and has been handed out as one, so nothing behind it may write: an endpoint that accepted a POST would silently give that power to every script already carrying a copy.

**The iOS and watch apps** live in `ios/` (see `ios/README.md`) and are never deployed — `deploy.sh` only sends `public/` and `lib/`. They are **completely independent of the website**: a fully native SwiftUI app with no web view, no login, no token and no network. All data is local — one `Codable` tree (`AppData` in `ios/Shared/Model.swift`) saved to a single `suite.json` in Application Support through `Store` (`ios/Shared/Store.swift`). Reminders, Calendar, Notes (plain text) and Habits are reimplemented natively, reusing the suite's ideas (folders/groups, repeats with month/year clamping, undated-first ordering, the slash-only US-order parser in `ios/Shared/Parse.swift`, two-press delete). The app starts empty. The watch is read-only: the phone builds a `WatchList` (`Store.watchList()`) and ships it over WatchConnectivity as the application context; the watch decodes and draws it. It's a separate codebase from the PHP suite — the two look alike but nothing is shared, so editing one never touches the other. `public/calmind/api/reminders.php` and the widget's `feed.php` still exist for the *web* widget/Scriptable use.

**Themes** (`public/akisthemes/`) is a workbench for building colour palettes, and is **deliberately not wired to anything**. It seeds itself with Aki's Bookshelf's eight as a starting point — a *copy* of those values, not a reference — so editing a colour here changes nothing in that app, and playing with colours can never repaint something someone is using; the `themes` test area exists mostly to hold that boundary. A palette is a name plus one colour per role, and the roles are the bookshelf's twelve (`--bg` … `--gold`) because they are a complete set for dressing a page, not because anything reads them from here. Stored per-user in `palettes-<user>.json`. Every value ends up inside a `style` attribute, so `clean_hex()` admits nothing but `#rrggbb` and `set_color` refuses an unknown role *and says so* — reporting success for something it didn't store would show a colour the file doesn't have until the next load quietly undid it. The picker saves on `change` rather than `input`, so dragging the colour wheel repaints live but writes once. Each palette shows a preview card wearing it and live WCAG contrast chips against its own page colour, anything under 4.5:1 flagged — the numbers are what actually decide whether a palette is usable. It is a standalone app like the bookshelf: its own chrome, no tab bar, `require_login()` with no per-user gate (palettes are per-user anyway, and gating it to one name would lock everyone else out of a tool that holds nothing private).

**Aki's Bookshelf** (`public/akisbookshelf/`) is a standalone app, not part of the tab bar: it gates on `current_user() !== 'aki'` after the shared login and renders its own chrome. Books come from the Open Library search API via `http_get()` (an 8-second `file_get_contents` with a User-Agent, the suite's only outbound HTTP). `book_cover()` prefers the locally cached `covers/<id>.webp` and falls back to `covers.openlibrary.org` — that cache is generated server-side and gitignored, so locally every cover comes from the network. Per-book notes are a sectioned list like the rest of the suite (`booknotes-<user>.json`). Folders are a Library-only idea here — the tiles a book's Goodreads shelves become; the book's own page has no folder controls. Its header follows the suite's: `books_header($title, $withEdit)` puts the Edit pencil beside the username at the same size, and edit-mode-only controls (like **Set cover**, which sits right of the book's details and level with the middle of the cover) hide behind `body.editing` as everywhere else.

**The bookshelf has its own themes** (`BOOK_THEMES`, in its `index.php`), and they are a separate setting from the suite's (`book_theme` vs `theme` in the same prefs file). The suite's `THEMES` (`lib/auth.php`) are now the same shape — full palettes — and the two tables share the same role columns; the bookshelf's repaint the page — `--bg`, `--surface`, `--surface-2`, `--line`, `--line-soft`, `--text`, `--text-dim`, `--muted`, `--accent`, `--accent-ink`, `--accent-soft`, `--gold`, emitted by `book_theme_css()` *after* `theme_css()` so this app's accent wins. **`midnight` is the original look and the default**, so an untouched bookshelf is unchanged. The other seven come from palettes Aki picked. Stored under `book_theme` in the same `prefs-<user>.json` as the suite theme but a separate key, so the two never move each other; the suite's accent row is hidden here (`.setmodal .setthemes`) since it would appear to do nothing, and the picker goes in `settings_modal_html()`'s long-unused `$extra` slot. `BOOK_THEMES_LIGHT` names the two cream themes, which set `color-scheme: light` — without it a light page opens black native dropdowns. **`--gold` is themed because it had to be**: the original `#f0b429` star-and-section gold is barely visible on cream. Where a palette had nothing that could do a job — an all-pastel set has no colour dark enough for text, and its mid-tones fail as an accent on their own pale ground — a member was deepened or lightened rather than dropped in flat; every theme clears ~4.5:1 for text, muted text, accent and gold on its own background. The rating stars' fill, the error red and the quote purple stay literal, like the suite's kind colours: they say what a thing *is*, not which theme you like. The shared settings window is repainted to the theme by local overrides in this app only, so a cream page doesn't open a black modal.

## UI conventions

Themed throughout, dark by default: **the suite's `THEMES` (`lib/auth.php`) are full palettes now, not accent swaps.** Every neutral in the apps reads a variable — `--bg` / `--surface` / `--surface-2` / `--line` / `--line-soft` / `--text` / `--text-dim` / `--muted` / `--gold` beside the existing `--accent` trio — emitted by `theme_css()` (`theme_vars()` is the one place the columns are named; the picker's swatches read it too). **The suite offers four themes — `midnight`, `sage`, `forest`, `olive` — the boards Draft 3 was judged on.** **`midnight` is the old `#111`/`#eee`/`#34d399` look and the default**, so an untouched account is unchanged; a legacy stored name (`green`, `rose`, or a retired theme like `blossom`/`dusk`/`neon`/`plum`) falls back to it. `THEMES_LIGHT` names the cream themes, which flip `color-scheme` so native controls follow, and every page's `<meta name="theme-color">` reads `theme_bg()`. The settings picker shows each theme as its own swatch (page colour + accent dot). Semantic colours stay literal: the kind palette, the error red, the shared-badge purple, and Habits' violet identity. New styles must use the variables — a hardcoded `#111`-family hex will look broken on Sage. `quick.php`, `feed.php`'s setup page and the login page emit `theme_css()` themselves (they don't use `chrome_styles()`); the login page always renders midnight (no user yet). Pill-shaped controls throughout. Reminders/events/notes have one palette suite-wide — `kind_color_css()` in `lib/util.php` emits it as `--k-reminder` / `--k-event` / `--k-note` (plus `-bg`/`-soft` and `--k-overdue`), and every dot, chip and tag reads those rather than a literal. The event blue is deliberately a blue (`#60a5fa`) and not a cyan, so it can't be read as the green at dot size; `cal_color_fix()` remaps calendars still holding the old `#38bdf8` **and bumps any colour stored under an earlier palette generation to the same slot in today's** — `palette_recolor()`/`pal_legacy()` (`lib/palette.php`) know every past generation, and folder, habit-section and shared-override colours go through the same bump on read, so a repaint never scrambles which folder was which colour. Shared chrome comes from `lib/chrome.php` and `lib/tabbar.php` (icon-only bottom bar). **The top bar is one row, 32px tall, in the same place in every app** (1.5rem from the top, 0.5rem of gap under its rule — the same small gap in every app), **with a rule under it**: back button and the app's name on the left; on the right, the app's own title controls (the folder/calendar picker, or Habits' Edit pencil), then the username, whose dropdown holds Settings and Log out. `render_user_menu()` takes a `$controls` slot that renders at the start of that right group — apps capture their picker HTML with `ob_start()` and pass it in. `.backbtn`, `.titlebtn` and `.usermenu .who` are sized together in `chrome_styles()`, so a new app only supplies what goes inside. Aki's Bookshelf repeats the same rules locally since it doesn't use `chrome_styles()`. Inputs use `font-size: 16px` so iOS doesn't zoom on focus. These are iOS home-screen PWAs — respect `env(safe-area-inset-*)`, and note `tabbar.php` intercepts same-origin clicks in `window.navigator.standalone` mode so links stay in the app.

**Edit mode.** Destructive controls (delete buttons, drag handles) are hidden unless `body.editing` is set. **The top-left back button becomes a black × while editing**, and that × leaves edit mode: `back_button()` emits both (`.backbtn.goback` and `.backbtn.exitedit`) into the one slot and CSS swaps them, so nothing beside them shifts. Aki's Bookshelf, which doesn't use `chrome_styles()`, repeats the pair itself. Every Completed toggle is the checked box `☑`, green when on. Reminders, Notes and the Calendar have **no Edit button at all**: you enter edit mode with a **long-press** (touch) or **double-click** (desktop) on a row or section — on a reminder that also opens its text inline, on a calendar row it opens the edit modal — and leave it by tapping empty space or pressing Escape. (Each app wires this itself, near its existing drag/inline-edit code.) Habits and the Bookshelf keep an Edit pencil of their own. Drag handles hide with `visibility: hidden`, not `display: none`, so entering edit mode doesn't nudge every line of text sideways. It is deliberately *not* persisted — every app starts out of edit mode, so opening the app or switching tabs never lands you in it. Across a POST→redirect the rule is **echo, never originate**: `keep_edit_script()` stamps `edit=1` onto any form submitted *while editing* (it listens for submit **and** patches `HTMLFormElement.prototype.submit`, since the rename fields commit programmatically and fire no event), the handler carries the posted flag back on its redirect, and the page turns edit on and strips the param with `history.replaceState` — so adding a section mid-edit doesn't kick you out, while a swipe-delete from outside edit mode never drags you in. A handler must never append `edit=1` on its own; the `editmode` test area runs each one bare and flagged to hold that line.

**User settings** live in the **username's own dropdown** — there is no settings `⋮` any more, and `settings_button()` is gone with it. The menu is the same two rows in every app, **Settings** then **Log out**, so preferences are always in the same place; Settings (`#setBtn`) closes the dropdown and opens `settings_modal_html/styles/script` (`lib/chrome.php`, emitted by `chrome_styles()`/`chrome_script()`; Aki's Bookshelf emits the modal and its own menu markup itself). Changing your password posts `change_password` to whatever page you're on — `require_login()` answers it and replies JSON. The **Change password** button sits on its own row (`.setpwrow`) directly under the password fields, *above* the Theme picker. The footer below is one row of three identical 40px round icon buttons, `justify-content: space-around` and all sharing the `.setact` class: **Share** (a share glyph — only when `$showShare` is passed, there's a partner, and `lib/sharing.php` is loaded, since not every app requires it), **Widget** (a phone glyph, linking to `/calmind/calendar/feed.php`; rendered in every app now rather than passed in as Calendar's `$extra`) and **Done** (a checkmark, in the accent as the primary action). The Share button opens the sharing window, closing settings first since the share modal sits a layer below. The `$extra` slot still exists but nothing uses it. Reminders' "Copy as Markdown" is *not* here — it's a share-icon button in the toolbar row, next to Completed, that copies the visible list from a hidden `#shareMdText` textarea. It's a personal tool, rendered only on the **sean** account (`$me === 'sean'`).

**Pages revive on return** (`revive_script()`, `lib/chrome.php`, in `chrome_script()`). iOS restores a home-screen PWA's page from memory on app-switch, and Safari's back-cache does the same — so a list sat stale, missing ticks made elsewhere (the Calendar panel, the widget, another device, a sharing partner). Every chrome page reloads itself when it comes back after **five clear seconds** away (and on a `pageshow` with `persisted`), unless it would interrupt something: never in edit mode, never while a field or the note editor holds focus, never with a window (`[class*="modal"].open`) or a swatch tray (`details[open]`) open. The reload stashes `scrollY` under the scroll keeper's key first, so the position survives.

**Scroll position survives an action.** Every mutation in the suite is a POST→redirect→GET, which normally drops you back at the top of the page — so ticking a reminder halfway down the list used to jump. `keep_scroll_script()` (`lib/chrome.php`, in `chrome_script()`) stashes `scrollY` in `sessionStorage` on submit and restores it on the next load, then forgets it, so a fresh visit still opens at the top. It hooks the `submit` event *and* patches `HTMLFormElement.prototype.submit`, because a programmatic `form.submit()` (the Calendar day panel's tick box and quick delete) fires no submit event at all.

**Swipe a row left to delete it** (`swipe_delete_styles()` / `swipe_delete_script()` in `lib/chrome.php`) — the way to delete one reminder or one day-panel item without turning edit mode on for the whole list. Mark the row `swipe-row` and give it a `needs-confirm` delete control: the gesture adds `swiped`, which reveals that control, and the swipe counts as the first press so it deletes on one tap. It stands down in edit mode, where dragging owns the row.

**Deleting is a two-press gesture** (`confirm_delete_styles()` / `confirm_delete_script()` in `lib/chrome.php`) — there is no `confirm()` box and no Undo button anywhere. Give the control class `needs-confirm`: the first press fills it red — the label never changes, since a `×` that became the word `Delete?` resized its row — and the second submits and the script injects a hidden `confirm=1`. Server handlers must require `!empty($_POST['confirm'])` before destroying anything, so a stale page can't delete on one tap. Pages that don't use `chrome_styles()`/`chrome_script()` (e.g. Aki's Bookshelf) emit the two helpers themselves.

**Icon buttons are circles.** Any button whose label is a glyph (`+`, `×`, pencils, swatches, ticks, the habit grid cells) wears `border-radius: 50%` — the rounded-square icon button is gone suite-wide. Text buttons (Save, Done, `+ Add date`) stay rectangles and pills. The tab bar's active highlight is the same idea: a fixed 36px circle centred behind the icon (absolutely positioned, so it can never move the tabs' spacing), not an inset-based pill.

**Every icon button is centred — check this before every deploy.** Any button whose label is a glyph rather than words (`+`, `×`, `‹ ›`, the chevrons, the round swatch and picker buttons, the settings footer's three `.setact`s) must carry `display: inline-flex; align-items: center; justify-content: center;`. A glyph left in a `display: block`/`inline-block` button sits on the text baseline with the font's own leading above it, so it rides high or low by a pixel or two — invisible in isolation, obvious the moment it sits beside another button. `line-height: 1` alone does not fix it, and neither does `text-align: center`, which only handles the horizontal half. This is the one rule to re-check by eye on every touched page before running `deploy.sh`: grep the diff for new buttons and confirm each one has the three properties.

**A row of buttons is one size.** Where several sit together — the Calendar's `Completed / + Add`, Reminders' `Completed / Copy-as-Markdown / (share)` — they share a height (32px) set on the row, not per button. **Adding a section** is now the `+` beside each folder's name in Reminders and Notes (`.fsec-add`, always shown — not gated on edit mode): a small pill that swaps itself for a name field and swaps back if you leave it empty, posting `add_section` with that folder so the section always lands somewhere clear — there is no toolbar "+ Section" any more, and Habits adds sections from its "Manage sections" window instead. **Adding a row** is the `+` on a section header. Labels are short — `+ Note` — not `+ New …`. A section header's `×` is pushed right with `margin-left: auto` and the header carries the rows' side padding, so it lands under the rows' `×`s.

The Calendar's day-panel buttons are the reference for button sizing across the suite: `padding: 0.35rem 0.9rem; font-size: 0.9rem; border-radius: 999px`, green (`#34d399` on `#06251b`, weight 700) for the primary action and outlined (`1px solid #333`/`#444`) for the rest. Manager windows (calendars, folders) share one shape too: `<h2>`, an add row with a green `+`, a list of rows each with an `×`, then a Done button. The Calendar manager's two parts (Calendars, Reminder folders) are collapsible `.cm-section`s — tap the `<h2>` to fold one, remembered in `localStorage`.

## Working here

- Commit granularly and deploy promptly; committing straight to `main` is fine.
- **Change a feature, change its test in the same commit; add a feature, add a test with it; fix a bug, add the case that would have caught it.** `php tools/test.php` is the run (about 15 seconds, no framework: it seeds a scratch data dir with the real seeders, boots `php -S` against it and drives the real pages over real HTTP) and `TESTING.md` is the map of what it covers and what still has to be checked by eye. That map is part of the same bargain — keep it in step, or a thing ends up in neither list and nobody is looking at it. Note what the harness *can't* see: it runs no JavaScript, so every gesture, drag and long-press is in the by-eye column, and that is where nearly every bug that has actually reached a phone has come from.
- Before every deploy, re-check that each `+`/icon button you touched is visually centred (`display: inline-flex; align-items: center; justify-content: center`) — see the icon-button rule under UI conventions.
- Match the existing style: procedural PHP, short helper functions with one-line docblocks, `e()` for escaping, inline `<style>`/`<script>` in the page.
- To exercise a page without credentials, drive it from the CLI: start a session, set `$_SESSION['auth']`/`$_SESSION['user']`, set `$_SERVER['REQUEST_URI']`, then `require` the page. That renders (or POSTs to) it exactly as the server would, and it's the fastest way to check a change end-to-end.

### Standing rules

- **Behaviour lives in `lib/`; a page holds plumbing.** If you can describe a
  rule in a sentence, it belongs in a helper with a test — not inlined in one
  app's `index.php`, where the next app reimplements it half a shade
  differently and the two drift apart for a year before anyone notices.
- **This repo is the spec the CalMind monorepo greps.** Its `CLAUDE.md` sends
  every "match prod" question here, so the CSS and PHP in this tree settle
  arguments over there. Changing a look is fine; changing it without saying so
  means the other codebase is now wrong and nobody knows it. Where this file
  and the code disagree, that is a question for Sean, not a side to pick.
- **Two sessions share this repo.** `git pull --autostash` first, stage
  explicit paths, never `git add -A` — another agent's half-finished work must
  not ride along on your commit.
- **Production is never touched unless Sean says so in that message.** A bare
  `./deploy.sh` is test-only for exactly this reason. A fix goes to test and
  prod together; a feature goes to test and waits for him before `promote`.
  Approval for one change is not approval for the next.
- **Anything that tests a deploy script must neuter `ssh`/`rsync` in its copy
  first.** In the sibling repo, a run that proved the consent gate worked — by
  removing the consent gate — went on to write production. The `deploy` test
  area here only reads the scripts as text and parses them with `bash -n`, and
  proves an idiom by running a one-line snippet rather than the script itself.
  Keep it that way.
- **Sean's data is his.** Reading his live suite to find a bug is fine and has
  found real ones. Writing to it, reordering his sections, or seeding over his
  account is not. `tools/seed-example.php` and `tools/seed-buddy.php` touch the
  demo accounts and nothing else — that is why they exist.

### Traps that have cost real time

- **A check that cannot fail looks exactly like one that passes.** Break the
  thing a new test guards and watch it go red before trusting it. This has
  already bitten here: the harness looked for `'Warning:'` in pages that render
  `<b>Warning</b>:`, so every PHP warning sailed through green for as long as
  that check existed. `quiet()` in `tools/test.php` is the repair.
- **The shell's working directory persists between Bash calls**, and a `cd`
  inside one announces nothing. Use absolute paths, or the next command runs
  somewhere you did not mean.
- **Comments state intent; the code may have drifted.** Trust the code and fix
  the comment. Two real bugs in the sibling repo came from reading one against
  the other.
- **Ask what happens when a write fails.** The expensive bugs here are the
  silent ones — a `store_write()` whose `false` goes nowhere, a suppressed
  `@file_put_contents`, a data dir the web user cannot write. That last one is
  exactly how a seeding run printed "Seeded…" over a hundred failed writes.
- **Some bugs exist only on the phone.** The by-eye column above covers what
  the harness cannot run; the device adds its own — `env(safe-area-inset-*)`,
  `window.navigator.standalone`, a fixed overlay that sits under the clock, a
  tap target that is comfortable with a mouse and cramped with a thumb. Open it
  on the phone before calling a layout done.
- **Prefer Sean's shapes to your imagination.** Invented test data agrees with
  whoever invented it. The seeders build realistic reminders, events and habit
  history on purpose, so there is a way to test against plausible shapes
  without going near his account.
